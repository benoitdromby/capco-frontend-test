# Decisions

## TICKET-001 — Applicant registration

- **API client scope.** `frontend/src/api/` (`client.ts`, `errors.ts`, `applicant-accounts.ts`) implements the full JSON:API media-type negotiation, the complete error-kind mapping from `docs/API-NOTES.md`, and empty-body-safe response parsing — all generic and reusable as-is. Deliberately **not** built yet, since registration (an unauthenticated one-shot POST) needs none of it: CSRF (`X-XSRF-TOKEN`) header attachment, retry/backoff beyond the root `QueryClient`'s existing `mutations.retry: false`, request cancellation, and any `useQuery`/query-key convention layer. These will be added when TICKET-002/003 first need them, not speculatively now.
- **New conventions introduced.** `frontend/src/api/` and `frontend/src/hooks/` are new, additive directories (not a reorganization of anything existing) establishing the "API calls live in a shared client, business logic lives in custom hooks" pattern required by AGENTS.md, for reuse by later tickets.
- **New DS additions.** `TextField`'s new `description` prop (lets guidance text stay visible even once an error is also shown — see below), and `Typography`/`Alert` becoming `forwardRef` (needed to move focus to a confirmation heading or an error alert on submit). Both intentionally generic so TICKET-002/003 can reuse them.
- **Non-field API error display is a plain function, not a DS component.** `frontend/src/api/error-messages.ts`'s `apiErrorMessage(error)` maps a non-field `ApiError` to display text (or `undefined` for `validation`, shown on fields instead) and is rendered through DS's existing `Alert` directly at the call site (`<Alert severity="error" tabIndex={-1}>{message}</Alert>`). An earlier version of this wrapped `Alert` in a new `DS/ApiErrorAlert` component; collapsed back to a plain function since `Alert` was already the generic, reusable piece, and a second DS component added without a second real call site yet would have been speculative.
- **"Special character" working assumption.** The contract (`docs/API-NOTES.md`, `openapi.json`) does not define what counts as a special character for the password policy. Implemented as "any character that is not a letter or a digit." The server remains the final authority; the client-side regex is a convenience check only.
- **Password guidance stays visible on error.** WCAG 3.3.2 requires instructions before input; rather than letting an error message replace that guidance (the original behavior), the password field now shows both at once via `TextField`'s new `description` (always visible) and `helperText`/`error` (shown only when invalid) props, both wired into the input's `aria-describedby`.
- **Rate-limit feedback is a static message, not a live countdown.** Avoids timer/re-render complexity and repeated screen-reader announcements; the response's `Retry-After` value is shown once ("Try again in N seconds"), and the user can simply resubmit.
- **Entered values are never cleared on a failed submit** (client-side validation, server validation, conflict, rate limit, or network failure) — only a successful submit ends the form's lifetime, by replacing it with a confirmation panel. This minimizes retyping after an error.
- **Editing a field after a failed submission discards the previous server error wholesale** via the mutation's `reset()`, rather than tracking per-field dismissal state on top of TanStack Query's own error state.
- **Successful registration replaces the form with a dedicated confirmation panel** (its own single `h1`, which receives focus) instead of layering a success banner over the still-visible form. Keeps exactly one `h1` per page and avoids a stale password field remaining in the DOM.
- **Validation runs on submit only** (no live/blur validation), matching the existing interaction pattern and keeping scope to what the ticket requires.
- **Automated accessibility checks run at the component-test layer (`jest-axe` in `-create-account-form.test.tsx`), not in the Playwright e2e specs.** Considered adding `@axe-core/playwright` to `register.spec.ts` for real-layout checks (e.g. color contrast) that jsdom can't do, but that's a new dependency and the e2e specs already indirectly exercise accessible roles/labels/names via Playwright's `getByRole`/`getByLabel` locators. Deliberately not added; revisit if a later ticket needs layout-dependent a11y coverage.

## TICKET-002 — Applicant login

- **Post-login destination always comes from the API's `href`, never from `returnTo`.** The pre-ticket stub navigated to `returnTo ?? '/applications/current'` — placeholder logic, not a deliberate design. The ticket is explicit ("route the Applicant to the journey URL returned by the API") and so is `docs/API-NOTES.md` ("navigate to href, never to a hard-coded URL"); neither mentions blending in `returnTo`. `returnTo` keeps its one remaining job — preserved across the "Create account" cross-link (`accountAccessHref`) — but no longer affects where a successful login lands. The returned `href` is still checked with the existing `isSafeJourneyPath` guard before navigating (open-redirect protection); if it ever failed that check, the form shows a generic error and does not navigate, rather than trusting the API response blindly.
- **The password field is not cleared after a failed login attempt**, consistent with TICKET-001's "never clear any field on failure." `docs/API-NOTES.md` explicitly calls this an open decision; the alternative (clear only the password, a common login-form convention) was considered, but the security benefit is negligible once the value has already left the browser in the POST body, and clearing costs UX (forced retyping). Easy to revisit if preferred.
- **`apiFieldErrors` promoted from `-create-account-validation.ts` into the shared `frontend/src/api/error-messages.ts`.** This is the "wait for a second real call site before extracting a shared helper" refactor discussed earlier in the project — login needed the identical `{email, password}` field-error mapping, so the extraction is now justified rather than speculative. `-sign-in-validation.ts` reuses the same `ApiFieldErrors` type as its own return type rather than declaring a redundant duplicate.
- **No CSRF handling added for login.** `POST /api/v1/applicant-sessions` has no `security` requirement in the OpenAPI contract (confirmed), same as registration. Still deferred to whichever TICKET-003 request first needs it (most likely logout or the form save/submit endpoints).
- **Duplicate-submission guard is an explicit `if (isPending) return` in the submit handler, not just `Button isPending`.** The button's pending state blocks a second *click*, but pressing Enter in a form field fires the form's `onSubmit` regardless of the submit button's own disabled state — the handler itself needs to check `isPending` to actually satisfy "prevent duplicate submissions while a request is pending." Covered by a test that forces a second `onSubmit` while the first request is still in flight.
- **`queryClient.clear()` runs inside `useApplicantLogin`'s own `onSuccess`, not a component effect** — the hook's guaranteed, once-per-success response to "the session just changed" (API-NOTES: "Clear the TanStack Query cache... the user and session have changed"), independent of component render timing.

## Codebase-wide — typed route paths via React Router's `href()`

- **Static internal route literals now go through `href()` (from `react-router`) instead of hand-typed strings**, in `routes/index.tsx`, `routes/api-docs-redirect.tsx`, `routes/applications/$applicationId.submitted.tsx`, `routes/-return-target.ts`'s `accountAccessHref`, and `routes/reviewer/applications.tsx`'s search-param navigation. `href()` is built into the installed React Router 8 (`@react-router/dev`'s typegen, which this project already runs as part of `npm run typecheck`) and checks every path against the real route tree in `routes.ts` — a typo or a route that doesn't exist is now a compile error instead of a silent runtime 404. Preferred over a hand-rolled path-constants module specifically because it has no second source of truth to drift from `routes.ts`: the "names" are generated from the route config itself.
- **Not applied everywhere** — deliberately skipped: `routes/api-docs.tsx`'s `/openapi.json` link (a static public asset, not a registered app route — `href()` would fail to compile there); `isSafeJourneyPath` in `-return-target.ts` (validates an untrusted *runtime* value returned by the API, not a compile-time-known route key, so `href()` doesn't apply by design); `test/handlers.ts`'s fixture `href: '/applications/current'` (simulates what the *server* returns, not a client-side navigation — using `href()` there would conflate the two). Also deferred: `routes/applications/current.tsx` and `routes/applications/$applicationId/$step.tsx`, both still fixture-stub code TICKET-003 is expected to substantially rewrite — applying this there now risks being throwaway work, and `href()`'s param typing wouldn't fully cover that file anyway (`:step` is typed as plain `string` by the route config, not a union of the actual allowed step names, so it catches a wrong route but not a misspelled step value).
- **Found, not fixed: `routes/reviewer/applications.tsx`'s "View"/"View application" links point to `/reviewer/applications/${id}`, a route that isn't registered in `routes.ts`.** Discovered while surveying for this change — applying `href()` there would have caught it immediately at compile time, which is itself the argument for doing this broadly over time. Left as-is since a reviewer-detail route isn't part of any ticket yet; worth fixing whenever that screen is built.
