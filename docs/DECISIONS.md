# Decisions

## TICKET-001 — Applicant registration

- **API client scope.** `frontend/src/api/` (`client.ts`, `errors.ts`, `applicant-accounts.ts`) implements the full JSON:API media-type negotiation, the complete error-kind mapping from `docs/API-NOTES.md`, and empty-body-safe response parsing — all generic and reusable as-is. Deliberately **not** built yet, since registration (an unauthenticated one-shot POST) needs none of it: CSRF (`X-XSRF-TOKEN`) header attachment, retry/backoff beyond the root `QueryClient`'s existing `mutations.retry: false`, request cancellation, and any `useQuery`/query-key convention layer. These will be added when TICKET-002/003 first need them, not speculatively now.
- **New conventions introduced.** `frontend/src/api/` and `frontend/src/hooks/` are new, additive directories (not a reorganization of anything existing) establishing the "API calls live in a shared client, business logic lives in custom hooks" pattern required by AGENTS.md, for reuse by later tickets.
- **New DS additions.** `TextField`'s new `description` prop (lets guidance text stay visible even once an error is also shown — see below), and `Typography`/`Alert` becoming `forwardRef` (needed to move focus to a confirmation heading or an error alert on submit). Both intentionally generic so TICKET-002/003 can reuse them.
- **Non-field API error display is a plain function, not a DS component.** `frontend/src/api/error-messages.ts`'s `apiErrorMessage(error)` maps a non-field `ApiError` to display text (or `undefined` for `validation`, shown on fields instead) and is rendered through DS's existing `Alert` directly at the call site (`<Alert severity="error" tabIndex={-1}>{message}</Alert>`). An earlier version of this wrapped `Alert` in a new `DS/ApiErrorAlert` component; collapsed back to a plain function since `Alert` was already the generic, reusable piece, and a second DS component added without a second real call site yet would have been speculative.
- **"Special character" working assumption.** The contract (`docs/API-NOTES.md`, `openapi.json`) does not define what counts as a special character for the password policy. Implemented as "any character that is not a letter or a digit." The server remains the final authority; the client-side regex is a convenience check only.
- **Password guidance stays visible on error.** WCAG 3.3.2 requires instructions before input; rather than letting an error message replace that guidance (the original behavior), the password field now shows both at once via `TextField`'s new `description` (always visible) and `helperText`/`error` (shown only when invalid) props, both wired into the input's `aria-describedby`.
- **Rate-limit feedback is a static message, not a live countdown.** Avoids timer/re-render complexity and repeated screen-reader announcements; the response's `Retry-After` value is shown once ("Try again in N seconds"), and the user can simply resubmit.
- **Entered values are never cleared on a failed submit** (client-side validation, server validation, conflict, rate limit, or network failure) — only a successful submit ends the form's lifetime, by replacing it with a confirmation panel. This minimizes retyping after an error.
- **Editing a field after a failed submission discards the previous server error wholesale** via the mutation's `reset()`, rather than tracking per-field dismissal state on top of TanStack Query's own error state.
- **Successful registration replaces the form with a dedicated confirmation panel** (its own single `h1`, which receives focus) instead of layering a success banner over the still-visible form. Keeps exactly one `h1` per page and avoids a stale password field remaining in the DOM.
- **Validation runs on submit only** (no live/blur validation), matching the existing interaction pattern and keeping scope to what the ticket requires.
- **Automated accessibility checks run at the component-test layer (`jest-axe` in `-create-account-form.test.tsx`), not in the Playwright e2e specs.** Considered adding `@axe-core/playwright` to `register.spec.ts` for real-layout checks (e.g. color contrast) that jsdom can't do, but that's a new dependency and the e2e specs already indirectly exercise accessible roles/labels/names via Playwright's `getByRole`/`getByLabel` locators. Deliberately not added; revisit if a later ticket needs layout-dependent a11y coverage.

## TICKET-002 — Applicant login

- **Post-login destination always comes from the API's `href`, never from `returnTo`.** The pre-ticket stub navigated to `returnTo ?? '/applications/current'` — placeholder logic, not a deliberate design. The ticket is explicit ("route the Applicant to the journey URL returned by the API") and so is `docs/API-NOTES.md` ("navigate to href, never to a hard-coded URL"); neither mentions blending in `returnTo`. `returnTo` keeps its one remaining job — preserved across the "Create account" cross-link (`accountAccessHref`) — but no longer affects where a successful login lands. The returned `href` is still checked with the existing `isSafeJourneyPath` guard before navigating (open-redirect protection); if it ever failed that check, the form shows a generic error and does not navigate, rather than trusting the API response blindly.
- **The password field is not cleared after a failed login attempt**, consistent with TICKET-001's "never clear any field on failure." `docs/API-NOTES.md` explicitly calls this an open decision; the alternative (clear only the password, a common login-form convention) was considered, but the security benefit is negligible once the value has already left the browser in the POST body, and clearing costs UX (forced retyping). Easy to revisit if preferred.
- **`apiFieldErrors` promoted from `-create-account-validation.ts` into the shared `frontend/src/api/error-messages.ts`.** This is the "wait for a second real call site before extracting a shared helper" refactor discussed earlier in the project — login needed the identical `{email, password}` field-error mapping, so the extraction is now justified rather than speculative. `-sign-in-validation.ts` reuses the same `ApiFieldErrors` type as its own return type rather than declaring a redundant duplicate.
- **No CSRF handling added for login.** `POST /api/v1/applicant-sessions` has no `security` requirement in the OpenAPI contract (confirmed), same as registration. Still deferred to whichever TICKET-003 request first needs it (most likely logout or the form save/submit endpoints).
- **Duplicate-submission guard is an explicit `if (isPending) return` in the submit handler, not just `Button isPending`.** The button's pending state blocks a second *click*, but pressing Enter in a form field fires the form's `onSubmit` regardless of the submit button's own disabled state — the handler itself needs to check `isPending` to actually satisfy "prevent duplicate submissions while a request is pending." Covered by a test that forces a second `onSubmit` while the first request is still in flight.
- **`queryClient.clear()` runs inside `useApplicantLogin`'s own `onSuccess`, not a component effect** — the hook's guaranteed, once-per-success response to "the session just changed" (API-NOTES: "Clear the TanStack Query cache... the user and session have changed"), independent of component render timing.

## Codebase-wide — typed route paths via React Router's `href()`

- **Static internal route literals now go through `href()` (from `react-router`) instead of hand-typed strings**, in `routes/index.tsx`, `routes/api-docs-redirect.tsx`, `routes/applications/$applicationId.submitted.tsx`, `routes/-return-target.ts`'s `accountAccessHref`, and `routes/reviewer/applications.tsx`'s search-param navigation. `href()` is built into the installed React Router 8 (`@react-router/dev`'s typegen, which this project already runs as part of `npm run typecheck`) and checks every path against the real route tree in `routes.ts` — a typo or a route that doesn't exist is now a compile error instead of a silent runtime 404. Preferred over a hand-rolled path-constants module specifically because it has no second source of truth to drift from `routes.ts`: the "names" are generated from the route config itself.
- **Not applied everywhere** — deliberately skipped: `routes/api-docs.tsx`'s `/openapi.json` link (a static public asset, not a registered app route — `href()` would fail to compile there); `isSafeJourneyPath` in `-return-target.ts` (validates an untrusted *runtime* value returned by the API, not a compile-time-known route key, so `href()` doesn't apply by design); `test/handlers.ts`'s fixture `href: '/applications/current'` (simulates what the *server* returns, not a client-side navigation — using `href()` there would conflate the two). Also deferred: `routes/applications/current.tsx` and `routes/applications/$applicationId/$step.tsx`, both still fixture-stub code TICKET-003 is expected to substantially rewrite — applying this there now risks being throwaway work, and `href()`'s param typing wouldn't fully cover that file anyway (`:step` is typed as plain `string` by the route config, not a union of the actual allowed step names, so it catches a wrong route but not a misspelled step value).
- **Found, not fixed: `routes/reviewer/applications.tsx`'s "View"/"View application" links point to `/reviewer/applications/${id}`, a route that isn't registered in `routes.ts`.** Discovered while surveying for this change — applying `href()` there would have caught it immediately at compile time, which is itself the argument for doing this broadly over time. Left as-is since a reviewer-detail route isn't part of any ticket yet; worth fixing whenever that screen is built.

## TICKET-003 — Save and resume Applicant KYC form

- **Document-evidence upload is in scope, despite the ticket text only naming "answers."** Live-verified that `identity-and-address` can never reach `complete` without `documentEvidence.present: true` (the server requires an uploaded JPG/PNG, independent of the text fields). You explicitly chose to implement the upload (`POST .../document-evidence`) rather than ship a step that can never complete. Final submission/review (`$applicationId.submitted.tsx`, the `review` step's Submit button) remains untouched and out of scope.
- **`POST /api/v1/applicant-applications` (create-or-get draft) requires `X-XSRF-TOKEN`, even though the OpenAPI spec does not list it as a `parameters` entry for that operation** — confirmed live (missing → 403 `access-denied`; present → 201/200). Unlike the form PATCH and document-evidence POST, which do document the header. A new, real contract-documentation inconsistency distinct from the ones already logged in `docs/API-NOTES.md` §5; added there too.
- **The draft is created when the journey starts** (`-current-application-journey.tsx`'s `onPrimaryAction`, from the `'start'` entry state), **not deferred to first save.** Resolves the open decision API-NOTES flagged. The route structure (`/applications/:applicationId/:step`) requires a real id to even construct the next URL, which rules out waiting for a save to happen first.
- **`csrfHeaders()` (new `frontend/src/api/csrf.ts`) is called explicitly at each authenticated, state-changing call site** (draft creation, form save, document upload, logout) rather than inferred automatically from HTTP method — registration and login are also POST/DELETE but need no CSRF, so method alone isn't a reliable signal. Needed no change to `apiRequest`'s signature; `headers` was already a plain passthrough.
- **`apiRequest` gained one small branch for a `FormData` body** (used only by the document-evidence upload): passed to `fetch` untouched, with no `Content-Type` set so the browser can add the multipart boundary. Chosen over a second, hand-rolled fetch helper that would duplicate the existing error/network handling for one endpoint.
- **409 `form-version-conflict` is handled by an explicit, user-clicked "Reload" action, never an automatic refetch.** `-step-form.tsx`'s `handleReload` awaits `refetch()` and re-seeds local `answers` directly from the value it resolves to — not from an effect watching the `form` prop. An earlier version used a `reloadToken` counter plus a guarded effect reacting to `form` changes; a real integration test caught a genuine race in that design (`await refetch()` resolving does not guarantee the *parent* component has already re-rendered with the fresh `form` prop by the time the next state update runs, so the effect could "lock in" against stale data). Reading the resolved value directly removes the race entirely and is simpler. The same design is why an incidental background refetch (e.g. the document upload invalidating the form query) never touches `answers`: nothing re-seeds local state except that one explicit call path.
- **Switching step or application id remounts the step form via a `key` prop** (`key={\`${applicationId}:${step}\`}` in `-current-application-step.tsx`), so a lazy `useState` initializer seeds `answers` exactly once per step with no empty-then-filled flash — distinct from, and simpler than, the reload mechanism above.
- **Continue saves, then conditionally advances** based on the save response's per-step `steps[].state === 'complete'` — not `currentStep`, whose enum (`personal-details | identity-and-address`) has no `'review'` member and so can't express the identity-and-address → review transition. If the step isn't complete, the form stays put and shows "Complete all required fields before continuing," now driven by the server's authoritative completion signal instead of the original stub's `reportValidity()`. This guarantees Continue never silently discards unsaved input by navigating past an incomplete step. Save remains a separate, always-available action that never navigates, satisfying "save when the user activates Save" as its own distinct, visible behavior (a persistent `role="status"` node alternating between empty / "Saved at HH:MM." / "Unsaved changes.").
- **Per-field client validation was added to the step form after manual testing, revisiting the original "skip it" decision above.** `-step-form-validation.ts` generates "required" rules from `stepFieldConfigs` (the existing single source of truth, not a second field list) — no stricter-than-contract rule anywhere. **Continue blocks on validation** (no API call on invalid input, mirroring registration): `validateStepForm` checks both completeness ("required") and format. The server-driven "Complete all required fields" alert stays as a fallback for completeness reasons the client can't see (identity-and-address's missing document isn't an `Answers` field). Focus-on-first-invalid-field is driven by a `validationAttempt` counter bumped only on a failed Continue, not by watching the live error object — with a dynamic, per-step field set there's no fixed effect-dependency list, and reacting to the error object directly would re-steal focus on every keystroke as errors clear one at a time.
- **Save never requires completeness, and after manual testing this was tightened to also never *display* a "required" error.** The first version of this change had Save compute and show the exact same errors as Continue (including "required") while still always calling the API — but showing a wall of red "required" messages the moment Save is clicked reads as the save being rejected, which contradicts TICKET-003's "show a clear saved state only after the API confirms success." Leaving a field empty and saving is a supported way to keep partial progress, not an error, so it shouldn't look like one. `validateStepFieldFormats` (new, in `-step-form-validation.ts`) is a second, narrower check used only by Save: it skips every "required" rule and only flags a value that's already been entered but has the wrong format (currently just a malformed email) — a genuine problem with the data itself, unlike "not done yet". Save also now clears any stale "complete all required fields" banner left over from an earlier failed Continue attempt, since choosing Save instead means the user isn't trying to complete the step right now.
- **Date of birth and expiry use native `<input type="date">`, not plain text.** The contract defines no date format at all (`Answers.dateOfBirth`/`expiry` are bare `{"type": "string"}`) — live-verified the server accepts `"not-a-date-at-all"` and `"3000-99-99"` with a 200, no validation whatsoever. Rather than inventing an unlisted format rule, format correctness is delegated to the browser's native picker, which always yields a clean `YYYY-MM-DD` string or nothing.
- **react-hook-form was considered and not adopted**, for the step form's new validation or anywhere else. Every `Answers` field is free text or boolean needing only a "required" check (confirmed above) — RHF's value (fewer re-renders on large uncontrolled forms, less boilerplate for complex rules) doesn't apply, and DS's `TextField`/checkbox wrap React Aria Components, so RHF would need `Controller` per field anyway, offsetting most of the savings. Stays consistent with the zod-plus-local-state pattern already used for registration/login.
- **Fixed a real, pre-existing bug affecting every form's field errors, not just the step form's new validation**: `DS/Primitives.module.css` had `.description[data-slot='errorMessage']`, but React Aria's `Text` renders a literal `slot="errorMessage"` DOM attribute, not `data-slot` — confirmed by reading the library source. The selector never matched, so field error text has never actually rendered in red, on registration, login, or now the step form, since it was written. Fixed to `.description[slot='errorMessage']`. This was undetectable by any jsdom-based component test (jsdom doesn't compute real CSS); caught only by manual testing in a real browser, and now guarded by two Playwright `toHaveCSS('color', 'rgb(180, 35, 24)')` assertions (`register.spec.ts` for the shared DS mechanism, `save-and-resume.spec.ts` for the step form's new validation UI).
- **Logout lives in `applications.tsx`** (the layout route already shared by exactly the three applicant-journey pages, previously an empty `<Outlet/>`). Its error handling stays minimal (an inline message, no navigation, no retry scaffolding) because the session cookie is only cleared server-side on a successful 204 — navigating away on a failed `DELETE` would misleadingly look logged-out while the server still holds the session; letting the user simply click "Log out" again is simpler and non-destructive.
- **Routes split into a thin route file + a colocated, prop-driven private component**, extending the `sign-in.tsx`/`-sign-in-form.tsx` pattern to `current.tsx` → `-current-application-journey.tsx` and `$step.tsx` → `-current-application-step.tsx` → `-step-form.tsx`. Additive siblings, not a reorganization of existing folders; done specifically so the real logic is unit/component-testable without a full router harness.
- **Found while building the e2e tests: once any draft exists — even one that was just created and never saved — the login response's `href` points directly at the in-progress step** (e.g. `/applications/{id}/identity-and-address`), not the generic `/applications/current`. Only a user with no draft at all gets the generic journey-entry href. No code change needed (the app already just navigates to whatever `href` the API returns, per TICKET-002's "never a hard-coded URL" decision) — but it means the journey page's `'resume'` entry state is reachable by direct navigation to `/applications/current`, not by a typical login once a draft exists. Worth knowing when writing future tests or UI copy. Noted in `docs/API-NOTES.md` too.
- **The KYC form's `email` field (personal-details) also gets a format check (`kind: 'email'` in `-form-steps.ts`), not just "required."** The contract defines no format for it either, but an obviously malformed contact email is worth catching client-side as a convenience, the same reasoning already applied to registration's account email — the server remains the final authority. Also switches that field's input `type` to `email` (same mechanism already used for the date fields' `type="date"`), for the native mobile-keyboard benefit.
